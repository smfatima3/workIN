# Recovery-focused revision 0.2.0 — 3 November 2026

## Decision

Pursue the question as an empirical recovery study. AIM's public safety agenda makes it a plausible collaborator; interest is not confirmed. The valuable contribution is a measured recovery boundary or safety–utility tradeoff under imperfect evidence, not the observation that copied memories survive.

## Audit and changes

| Audit finding | Revision |
|---|---|
| Perfect ancestry made selective deletion an idealized demonstration | Executable recovery stage masks lineage with full/partial/no availability; full history is evaluator-only |
| Verification resources were not bounded across a rollout | Shared per-robot observation allowances cover write, use and shield reads across tasks |
| Local shield bypassed the declared sensor-failure flag and could poll repeatedly | Shield now obeys the same sensor failure, gets one read per robot/task, and charges the shared allowance; unknown remains an explicitly documented fail-open policy |
| Utility analysis paired only E/A | Every recovery now has clean and poisoned paired cost/utility contrasts; added recovery head-to-head risk contrasts |
| Physical pairing was asserted but not automatically checked | Initial physics-state hashes are recorded and compared within matched blocks |
| Full-reset disadvantage depended partly on a fixed artificial docking penalty | Penalty is configurable; zero-cost sensitivity required before efficiency claims |
| Correct descendant deletion was not quantified | Correct/false record-removal counts and correct-record removal rate added |
| RQ could imply a predetermined new repair method | Method-neutral RQ, falsifiable hypotheses, explicit causal estimand and prior-art boundary |

## What remains unimplemented

Mixed correct/incorrect records with independent alternative support; retained derived maps/plans/queued commands; alert-latency and committed-action recovery; natural-language summaries; faithful published-method integration; another physical platform and real model results. Do not describe these as completed tests. No novelty or deployment benefit is established by fixture behavior.

## Evidence preservation

Previous source package: `archive/v0.1.0_code_and_smoke.zip`. Existing fixture logs remain unchanged. New code has new manifests. `VERIFICATION.md` records revision-specific validation; there are no actual-model scientific findings.
